# 阶段 Agent 设计（草案）

> 状态：P1（角色化）已实施，P2–P5 未实施。2026-11-19。落地时的取舍见第 13 节。
> 范围：「研发交付」流程的 AI 阶段，按大维度分成四个角色：讨论、实施、测试、发布。

## 1 目标

每个阶段由一个**独立的 agent** 处理，它有自己的：

- **身份**：角色定义，包括职责、输入、输出和禁止事项；
- **技能**：只给这个角色用的 skills；
- **记忆**：跨任务积累的经验，按角色、按项目各存一份；
- **上下文**：本任务里只看到上游交给它的东西。

这样做想得到三点：

- 每个角色可以单独调优，包括换提示词、换模型、加 skill，而不影响其他角色；
- 同类错误不再每张卡重犯一遍；
- 测试能真正独立于实施。

**不做**：

- 不放宽 DSH 沙箱；
- 不修改 DSH 本体，只改插件补丁和套件；
- 不在阶段之间共享会话上下文。

## 2 现状（已查证）

下面是读 dsh-kanban 1.12.1 的 Workflow 引擎（`workflow/`）和 DSH 0.2.2-rc.5 的结论。

| 要素 | 现在 | 依据 |
| --- | --- | --- |
| 上下文 | 每次执行阶段都新建一个会话，会话不能复用。阶段之间靠文件和 `workflow-handoff` 摘要交接。 | `dsh-adapter.js` 的 `run()`：会话已存在就报 `WORKFLOW_REUSE_FORBIDDEN` |
| 交接 | 引擎会把之前各阶段的 handoff（conclusions / openIssues / nextActions）作为 previousStages 交给下一阶段，并要求先读标了 needsRead 的报告。 | `runner.js` 的系统说明 |
| 模型 | 阶段定义支持 `modelSelection`，只有 agent 阶段能配。 | `store.js` 的定义校验 |
| 阶段字段 | 只允许 `id / kind / title / prompt / returnStageId / modelSelection`，多一个字段就校验失败。 | `store.js` 的 `exactKeys` |
| 打回 | 只有 review（人工关卡）能打回，而且只能打回到固定的、更早的 agent 阶段。agent 阶段不能自己回到上游。 | `store.js` |
| 身份 | 阶段提示词只是一个指针，指向 WORKFLOW.md 的「0 通用规则」加本阶段小节。所有角色读同一份手册。 | `workflows.json` |
| 预设 | 所有阶段都用默认 agent 预设：`presets.resolve()` 不带参数。预设本质上是一组模块开关，看不出能挑选单个 skill。 | `dsh-adapter.js`；DSH 的 `AgentPresetComposition` 类型 |
| Skills | 项目根目录按 `.git` 向上查找。阶段的工作目录 `<项目>/.dsh/workflow-artifacts/<taskId>/` 向上能找到 `<项目>`，所以**所有阶段看到同一套 skills**：`<项目>/.dsh/skills`、`<项目>/.agents/skills` 和 `~/.dsh/skills`。 | DSH 的 `findProjectRoot`，默认标记 `.git` |
| 记忆 | 没有跨任务记忆，每张卡都从零开始。 | — |
| 写权限 | 阶段只能写 `<ART>`，`<项目>` 只读。`<项目>/.dsh/` 已在 .gitignore 里（演示项目已确认）。 | WORKFLOW.md「沙箱」 |

**结论**：上下文隔离已经有了，缺的是**角色身份、按角色的技能、角色记忆**，以及一份写死的**交接契约**。

## 3 角色划分

| 角色 | id | 负责的阶段 | 一句话 |
| --- | --- | --- | --- |
| 讨论 | `discuss` | discuss | 把一句话需求变成可测的 PRD、技术方案和用例，列出要你拍板的问题 |
| 实施 | `build` | plan、code | 按确认过的方案写计划和代码，测试先行 |
| 测试 | `test` | test、prep | 独立验证，找问题；准备验收清单和发布说明 |
| 发布 | `release` | release | 唯一能写主分支的角色：合并、打 tag、部署、回滚 |

讨论确认和验收这两个人工关卡不是 agent，仍由你在看板上处理。讨论角色暂不拆成「需求」和「技术」两个，因为现在只有一个讨论关卡；需要时再拆。

### 3.1 讨论 agent（discuss）

- **输入**：卡片描述（任务输入）、项目代码和文档（只读）、角色记忆。
- **输出**：`<D>/prd.md`、`tech.md`、`cases.md`（REQ），或 `bug.md` / `brief.md`；用例库条目；草稿格式回复，含「待你拍板」。
- **Skills**：需求澄清、方案对比（至少一个备选和取舍）、代码库调研、用例设计。
- **记忆重点**：
  - 项目的领域词汇和约定；
  - 你的偏好，比如喜欢最小方案、不要引入新依赖；
  - 历次在讨论确认关卡被打回的原因。
- **模型**：推理最强的。
- **禁止**：写业务代码；替你做「待你拍板」里的决定。

### 3.2 实施 agent（build）

- **输入**：讨论产出（只读文档，不看讨论过程）、验收反馈（返工时）、测试缺陷清单（打回时）、角色记忆。
- **输出**：`<D>/PLAN.md`（含返工节、偏离计划节）、代码和测试、提交。
- **Skills**：TDD、项目编码规范、调试、重构。
- **记忆重点**：构建和启动命令、项目里的坑、被测试或验收打回过的原因、常用的修法。
- **模型**：编码能力强的。
- **禁止**：修改已确认的方案而不报 `阻塞：设计问题`；删改测试来让测试通过。

### 3.3 测试 agent（test）

- **输入**：PRD / brief 里的验收标准、用例、代码改动（diff）、TEST_STRATEGY 的命令、角色记忆。**不读 PLAN.md 的实现思路**，只把它的步骤清单当范围参考，保持对抗性。
- **输出**：
  - test 阶段：`<D>/test-report.md` 和缺陷清单 `<D>/defects.md`；
  - prep 阶段：`<D>/release.md`、CHANGELOG 条目、验收清单。
- **Skills**：用例设计、端到端测试、探索式测试、验收清单编写、测试环境部署。
- **记忆重点**：这个项目常见的缺陷模式、不稳定的测试、测试环境怎么起、哪些模块需要回归。
- **模型**：推理强的，可以和实施用不同厂商的模型，减少同源盲区。
- **禁止**：修改业务代码（见第 7 节）；把失败用例改成跳过。

### 3.4 发布 agent（release）

- **输入**：`<D>/release.md`、`docs/ops/DEPLOY.md` 的「生产」「冒烟」「回滚」节、角色记忆。
- **输出**：`<ART>/release.sh`、发布结果首行（已发布 / 未发布 / 已回滚）。
- **Skills**：语义化版本、发布脚本模板、回滚。
- **记忆重点**：发布脚本的坑、历次发布事故和处理方法。
- **模型**：便宜的即可，步骤固定。
- **禁止**：脚本以外的任何写 `<项目>` 操作；申请第二次提权。

## 4 角色定义文件

每个角色一个目录，放在套件里，跨项目共用：

```
dsh-kanban-flow-kit/agents/
  discuss/
    AGENT.md        角色定义
    memory.md       角色通用记忆（跨项目）
    skills/<name>/SKILL.md
  build/   ...
  test/    ...
  release/ ...
```

`AGENT.md` 固定为下面这些小节，方便对比和维护：

```markdown
# <角色名> agent
## 你是谁        一段话的身份和目标
## 负责的阶段    阶段 id 和每个阶段的具体步骤（从 WORKFLOW.md 第 2 节迁过来）
## 输入          必读、可读、不读（不读的写清楚，比如测试不读 PLAN 的实现思路）
## 输出          文件、回复首行格式、交接卡
## 可用技能      skills/ 下的清单，以及什么时候用
## 禁止          硬约束
## 记忆          开始前读哪些记忆，结束时怎么写经验候选
```

WORKFLOW.md 保留「0 通用规则」、文档地图、关卡清单和看板约定；第 2 节「各阶段」的内容迁到各角色的 AGENT.md。

阶段提示词改为：

```
你是「<角色>」agent。依次完整阅读：
1. 原项目目录下 docs/process/WORKFLOW.md 的「0 通用规则」
2. 套件 agents/<角色>/AGENT.md 中「<阶段>」部分
3. 记忆：agents/<角色>/memory.md 和 <项目>/.dsh/agents/<角色>/memory.md（不存在就跳过）
严格按其执行本阶段。任务输入首行是「<ID> <标题>」。
```

套件路径需要在项目接入时写进 `docs/process/` 或用环境约定，第一期落地时确定。阶段会话对套件目录有没有读权限，也需要验证（见第 12 节）。

## 5 交接契约

角色之间**只通过文件交接**：

- 每个文件有固定的位置和格式；
- 上游写什么、下游必须读什么，都写死；
- 角色可以单独替换。

引擎自带的 `workflow-handoff` 摘要继续保留，作为导航；契约文件是正文。

### 5.1 交接卡

每个角色的主产出文件开头加一段交接卡：

```markdown
<!-- 交接卡 -->
| 项 | 内容 |
| --- | --- |
| 来自 | discuss（第 2 轮） |
| 目标 | 一句话 |
| 已决定 | Q1=A（你拍板）、方案选 X |
| 约束 | 不引入新依赖；兼容旧数据 |
| 未决 / 风险 | …… |
| 下游必读 | prd.md#验收标准、cases.md#覆盖矩阵 |
```

### 5.2 读写矩阵

| 文件（`<D>/`） | 讨论 | 实施 | 测试 | 发布 |
| --- | --- | --- | --- | --- |
| prd.md / bug.md / brief.md | 写 | 读 | 读 | — |
| tech.md | 写 | 读 | 可读 | — |
| cases.md、用例库 | 写 | 读 | 读、补充 | — |
| PLAN.md | — | 写 | 只读步骤清单 | — |
| defects.md | — | 读、逐条回应 | 写 | — |
| test-report.md | — | — | 写 | 读结论 |
| release.md、CHANGELOG | — | — | 写 | 读 |

## 6 记忆

### 6.1 三层

| 层 | 位置 | 内容 | 谁写 |
| --- | --- | --- | --- |
| 角色通用 | 套件 `agents/<角色>/memory.md` | 跨项目都成立的经验，比如「先跑已有测试再写新测试」 | 人（从项目记忆里提炼） |
| 项目 | `<项目>/.dsh/agents/<角色>/memory.md` | 这个项目特有的经验，比如构建命令、坑、偏好 | 同步桥，经你确认后写入 |
| 任务 | 本卡的交接文件和评论 | 这一张卡的上下文 | 各阶段 |

项目记忆放在 `.dsh/` 下：它已被 gitignore，写入不会弄脏主工作区。发布脚本的前置检查要求主工作区干净，写到受 git 管理的位置会让发布失败。

### 6.2 写入路径

阶段会话只能写 `<ART>`，不能直接改记忆文件。写入走这条路：

1. 阶段结束前，在 `<ART>/lessons/<阶段>.md` 写 0 到 3 条**经验候选**。每条包括：
   - 一句话结论；
   - 触发场景；
   - 证据，比如哪次失败、哪个文件；
   - 建议写入哪一层。
2. 同步桥读到经验候选后，以「【记忆候选｜<角色>】」评论贴到卡片上，每条带编号。
3. 你在卡片里回复「记住 1 3」或「都不要」。同步桥把选中的条目追加到项目记忆，并回一条评论确认。
4. 角色通用记忆不自动写。你觉得某条经验跨项目成立时，手动搬到套件里。

### 6.3 控制质量

- **条数上限**：每个角色的项目记忆最多 40 条。超出时，同步桥在评论里提示你合并或删除，不自动丢弃。
- **格式**：每条一行结论，下面缩进写场景和来源卡号，方便日后追溯和删除。
- **去重**：经验候选和已有条目重复时，同步桥标注「已存在」，不重复写入。
- **只记可复用的经验**：不记一次性事实，比如某个 bug 的具体修法，那些应该写在卡片和提交里。

## 7 实施和测试的循环

**现状**：test 阶段发现失败后自己修代码，最多 5 轮。这和「测试独立于实施」冲突：测试 agent 改了代码，就是在验证自己的修改。

**方案**（推荐）：测试只报告，修复回到实施角色。

```
code → test → ◇测试关卡 →(有缺陷) 回到 code
                      →(通过)   prep → ◆验收 → release
```

- 新增一个 review 阶段 `g_test`，`returnStageId` 是 `code`。
- test 阶段只运行测试并写 `defects.md`，回复首行是 `测试通过` 或 `测试未通过 N 项`。
- **由同步桥自动决定这个关卡**：
  - 测试通过 → 同步桥代为「通过」；
  - 未通过 → 同步桥以缺陷清单作为反馈「打回」到 code；
  - 第 5 轮仍未通过 → 不再自动打回，给卡片打「待人工确认」，由你决定继续、改方案还是终止。
- 自动决定在活动记录里标注来源 `bridge-auto`，并在卡片评论里说明，和你的人工决定区分开。
- 实施角色在打回后先逐条回应 `defects.md`（修了、不同意并说明理由），再修复。

**备选**：保留 test 阶段内修复，但让测试 agent 用子代理按实施角色的 AGENT.md 去修。改动小，但修复过程不可见，测试仍在验证「同一个阶段里」的改动，独立性弱。不推荐。

## 8 Skills 隔离

DSH 按项目根目录加载 skills，所有阶段的项目根相同，所以无法原生按阶段隔离。分两步走：

1. **软隔离（第一期，零补丁）**：每个角色的 skills 放在套件的 `agents/<角色>/skills/` 下，不注册到 DSH。AGENT.md 的「可用技能」列出路径，由 agent 按需读取 SKILL.md。项目里已有的通用 skills 仍然对所有阶段可见。
2. **硬隔离（第三期，需要补丁）**：给插件打补丁，在阶段上增加一个预设字段，执行时用 `presets.resolve(<id>)` 加载对应的 agent 预设。需要同时改两处：
   - `store.js` 的字段白名单；
   - `dsh-adapter.js` 的执行逻辑。

   做之前要先确认 DSH 的预设能控制什么，比如能否限定 skill 目录、工具和系统提示词（见第 12 节）。

## 9 模型

- 每个 agent 阶段在 Workflow 页面单独选模型：讨论和测试用推理强的；实施用编码强的；发布用便宜的。
- 实施和测试最好用不同的模型，减少同源盲区。
- 引擎更新定义时会保留 agent 阶段原有的 `modelSelection`，所以在聊天里改提示词不会冲掉模型设置（需验证，见第 12 节）。

## 10 看板呈现

- 同步桥写的阶段评论里带上角色名，评论头像从统一的「AI」改成按角色显示：讨论、实施、测试、发布，各用一种颜色。这接上已经完成的 GitLab 风格评论界面。
- 描述末尾「阶段成果」表增加一列「角色」。
- 记忆候选评论单独用一种样式，提示你可以回复「记住 …」。

## 11 落地分期

| 期 | 内容 | 需要补丁 | 完成标准 |
| --- | --- | --- | --- |
| P1 角色化 | 拆出四个 AGENT.md；改阶段提示词；交接卡；按角色配模型 | 否 | 演示项目走通一张 REQ，各阶段按 AGENT.md 执行，交接卡齐全 |
| P2 测试独立 | test 只报告；新增 `g_test`；同步桥自动决定、5 轮上限 | 只改同步桥 | 故意埋一个缺陷，能看到测试 → 打回实施 → 修复 → 测试通过 |
| P3 记忆 | 经验候选、看板确认、写入项目记忆；条数上限和去重 | 只改同步桥 | 第二张同类卡能读到并用上第一张卡沉淀的经验 |
| P4 技能隔离 | 按阶段加载 agent 预设 | 是（插件） | 不同阶段会话的可用 skills 不同 |
| P5 看板角色化 | 按角色的评论头像、阶段成果表的角色列 | 是（前端） | 卡片上一眼看出哪条评论来自哪个角色 |

P1 到 P3 不依赖 DSH 内部能力，可以先做。P4 要先完成第 12 节的验证。

## 12 待决和待验证

**待你决定**（括号里是建议）：

1. 讨论角色要不要拆成需求和技术两个？（先不拆）
2. 记忆写入要不要你逐条确认？（要，至少在前几十张卡里）
3. 测试 agent 是否严格不看实施思路？（是）
4. 测试关卡由同步桥自动决定，你能接受吗？（能。这样测试和修复的循环不用人盯，5 轮后才找你）

**待验证**：

1. 阶段会话能不能读套件目录？读不了就在项目接入时把 `agents/` 复制到 `<项目>/docs/process/agents/`。
2. DSH 的 agent 预设能控制什么：能否限定 skill 目录、工具和系统提示词？这决定 P4 的做法。
3. 通过聊天工具更新流程定义时，阶段的 `modelSelection` 是否保留？引擎的管理工具在展示定义时会去掉这个字段，但更新时会沿用旧值。
4. 新增 `g_test` 关卡后，同步桥代为决定关卡的动作，在 Workflow 任务详情里如何显示，会不会和人工审核混淆。

## 13 P1 落地记录
